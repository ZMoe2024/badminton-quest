# 场地查询性能

2026-09-20：第一阶段减少重复防护初始化，不改变场地实时查询语义。

## 公开脚本缓存

`loader_cache.py` 在工作进程内缓存学校公开防护脚本的解析模板：

- 仅接受明确 `public` 的响应；`private`、`no-store`、带 Set-Cookie，或随身份/未知请求头变化的响应不缓存。
- 遵守 max-age、Age、no-cache；新鲜期最多一小时，过期用 ETag 条件请求。
- URL 变化重新下载；内容哈希相同复用解析结果；最多保留 8 份资源和 8 份解析模板。
- 并发查询首次使用同一脚本时，只下载和解析一次。
- 不缓存 Cookie、Token、账号上下文或生成好的请求参数。
- 旧模板无法解码当前首页时，重新获取一次脚本。HTTP 400/412 会清除相关脚本缓存和当前生成器，供后续查询重新初始化，不重放当前业务请求。

每次新建客户端仍从学校获取当前首页和独立防护上下文。缓存不会把动态参数写死。

## 同次查询复用客户端

`query_scope.py` 为界面的 availability、catalog、records 操作建立独立作用域。会话验证返回更新后的 Cookie 后，目录和占用查询可借用同一个客户端及连接池，操作结束统一关闭。

凭据键包含 Token、当前用户、User-Agent、Cookie 域/路径/名称/值。不同账号、凭据或并发操作不共用客户端。作用域通过 ContextVar 隔离；全馆查询仍使用最多三条独立查询通道，各通道独占会话和生成器。

预约、付款没有加入此复用作用域；身份、最终可预约状态、金额、幂等和不确定结果处理保持原样。场地占用、锁定等查询结果没有增加缓存。

按正常代码路径，首次单场地查询包含目录时，防护初始化从三次变为一次，学校 HTTP 请求从约 16 次降到约 12 次；脚本缓存命中后约 11 次。后续不含目录查询为约 11 次，脚本缓存命中后约 10 次。异常恢复或登录续期会增加请求。

## 验证

`python -m unittest discover -s badminton_reservation/tests -q`

新增测试覆盖缓存期限、ETag 更新、脚本版本变化、拒绝缓存私有响应、并发去重、缓存失效、账号隔离、Cookie 更新后的连接复用、失败清理，以及真实 probe/目录/占用函数之间的客户端复用。测试不提交真实预约或付款。

测量时应分别记录冷查询、缓存命中的热查询、账号工作进程冷启动和学校网络等待。公开防护初始化基准不代表完整的已登录场地查询耗时。
